## 2. 产品目标

Sekai 不是单纯的地形生成器，而是面向世界观作者的完整世界生成、解释与编辑工具。主要用途是辅助创作设定和历史。

产品需要同时提供：

1. 一个在指定年代内部自洽的完整世界快照；
2. 一条能够解释当前世界如何形成的历史；
3. 自然、魔法与社会因素之间可追溯的因果关系；
4. 作者对初始条件、规则和历史事件的人工干预；
5. 修改上游条件后对受影响下游内容进行可控重算；
6. 用独立显示模块检查每个中间字段和最终地图。

“完整产品设计”不等于一次实现全部功能，而是从第一天就确定完整领域边界、稳定数据契约和扩展机制，避免以后为了气候、魔法或历史推翻底层模型。

## 3. 已确认的设计决策

### 3.1 有历史的当前世界

产品形态采用“有历史的当前世界”，而不是只有最终结果的静态生成器，也不是持续实时运行的沙盒。

- 用户选择一个目标年代，系统生成该年代的世界快照。
- 系统保存迁徙、建城、文化分化、技术传播、国家兴亡、战争、贸易和灾害等编年史。
- 历史采用确定性的离线阶段或事件演化，可以重放和局部重算。
- 每个重要结果保留来源，例如城市选址、边界形成、人口迁移和国家冲突的原因。
- 自然世界是人类历史的底座；社会环境必须在自然环境之后生成。
- 自然过程不必全部使用时间积分。板块地形可以一次性合成；火山、气候变化和魔灾等慢变量可以作为历史事件介入。

### 3.2 平面优先，保留公共拓扑契约

- 近期目标是平面地图。
- 暂不实现球面 Goldberg 网格或完整球面板块运动。
- 地质、水文、气候和社会算法不能直接依赖 egui 坐标或特定 Voronoi 实现。
- 公共接口应依赖拓扑、邻接、面积、边长、位置和距离等语义，以便以后接入周期矩形或球面拓扑。
- 不为尚未实现的球面能力增加大量抽象成本，但禁止把平面细节泄露到所有领域模块。

### 3.3 物理板块碰撞是地形主因

- 地形应由板块、地壳和局部边界事件驱动，而不是先生成椭圆大陆再给板块适配大陆。
- 采用 Gleba 风格的一次性构造事件合成，不开发昂贵的地质时间积分。
- 逐边或逐短边界段计算相对运动，区分汇聚、离散、走滑和弱边界。
- 板块与地壳分离；一块板块将来可以同时承载大陆壳与海洋壳。
- 相邻板块应有非共动约束，避免大量没有构造意义的板块边界。
- 连续、同类且方向相近的边界边先聚合为边界段，再生成距离场和地貌。

### 3.4 高程采用“均衡基准 + 事件 stamping”

已选择综合高程模型：

```text
crust_base = isostasy(crust_type, crust_thickness, crust_density)

elevation =
    crust_base
    + coast_profile
    + sum(tectonic_event_fields)
    + hotspot_field
    + regional_noise
    + detail_noise
```

- 地壳均衡提供大陆、洋盆和宽阔高原的物理基准。
- 构造事件 stamping 提供褶皱山脊、海沟、火山弧、洋中脊、裂谷和断层等局部形态。
- 海平面由统一基准或全局水量求解，不再用多个阈值反复切割。
- 高程全程使用带单位的浮点数；`u8` 只能是显示或导出派生值。

### 3.5 艺术家输入进入因果链

用户不应只在最终高度图上涂改。

作者可编辑：

- 板块种子、边界意图、运动方向和速度；
- 大陆壳/海洋壳分布、地壳厚度和岩性；
- 热点、撞击、指定造山带和异常事件；
- 魔力源、地脉、结界、传送门和世界法则；
- 历史中的关键事件与约束。

这些输入与程序生成的数据写入相同的类型化字段或事件队列。后续地形、侵蚀、水文、气候、生态和历史对人工输入与自动输入一视同仁。

当前椭圆大陆掩膜可以保留，但只能作为“作者没有指定地壳时的默认初始条件”，不能继续充当隐藏的最终大陆生成规则。

### 3.6 先确定地图要素，再定架构，再做独立显示

用户明确拒绝“先做极简第一版再补设计”。顺序必须是：

1. 确定完整产品需要表达的地图要素和历史实体；
2. 建立能容纳这些要素的可扩展数据与生成架构；
3. 实现独立显示模块，并验证基础字段和渲染正确；
4. 再按依赖顺序实现自然与社会内容。

显示模块是验证生成系统的前置工具，不是最后的美化阶段。

### 3.7 类地球底座 + 可选魔法

这是一个奇幻世界生成器。世界默认遵循类地球自然规律，但魔法必须能真实介入自然与社会因果链。

关闭魔法规则包后，基础世界仍然完整可生成。开启后，魔法可以影响：

- 地形、重力和材料性质；
- 温度、降水、风、洋流和季节；
- 水文、生态、物种和资源；
- 交通、迁徙、聚落、经济和战争；
- 历史事件、文化、宗教和国家制度。

魔法不是最终地图上的装饰层，也不能直接随意改写渲染颜色或内部数组。它通过稳定的语义接口提交字段、作用量、约束和事件，由世界引擎重算后续阶段。

更准确地说：

> 魔法的定义与具体生成算法解耦；魔法产生的数据和因果会有意影响世界生成。

示例：

| 魔法定义 | 提交给世界引擎 | 下游结果 |
|---|---|---|
| 永冬诅咒 | 局部负热量强迫 | 降温、积雪、河流冻结、生态变化、人口迁出 |
| 地脉节点 | 魔力源和传播规则 | 魔法生态、资源富集、法师聚落和争夺 |
| 浮空岛 | 悬浮约束和地形事件 | 独立地形、水循环、交通与聚落条件 |
| 传送门 | 空间/交通图特殊边 | 改变贸易、迁徙、战争和国家边界 |

### 3.8 两级魔法扩展权限

用户已同意把魔法扩展分成两级：

1. **普通魔法规则包**
   - 通过局部或区域字段、作用量、约束和事件影响世界；
   - 不能任意替换核心存储或绕过依赖关系；
   - 适合魔力场、地脉、诅咒、神迹、魔法生态和传送门。

2. **世界法则包**
   - 可以改变全局常量或核心规律；
   - 适合重力、昼夜、天体、元素循环、位面结构等设定；
   - 必须显式声明被替换的能力与兼容要求；
   - 普通规则包不自动获得这种权限。

目前倾向普通规则包使用数据驱动定义，并为未来脚本扩展保留稳定接口；脚本语言、沙箱和版本策略尚未最终决定。

### 4.2 实际实现与旧架构文档不一致

旧 `REQUIREMENTS.md`、`ARCHITECTURE.md` 和 `ALGORITHMS.md` 描述了完整自然与社会系统，但多数内容是愿景而非现状。

当前关键事实：

- `CellsData` 只有 `height: Vec<u8>`。
- 板块、地壳、边界事件和中间字段在主流程末端丢失。
- 高度渲染在 CPU 每帧把所有高度转为颜色，并重新展开、上传 Voronoi 三角形数据。
- `app.rs` 为不同渲染器重复进行 Delaunay 三角剖分。
- 生成、模型、UI 和 GPU 之间没有稳定的字段或快照契约。
- 旧文档中的线性 `GeneratorPipeline`、完整图层管理器和大量生成模块并未实际存在。

### 4.3 已完成的审计结论

此前会话已经核实：

- 当前生产地形实质上是椭圆海陆掩膜、板块 ID 分区、距离场、随机内陆峰、噪声和两轮后处理的组合；
- 板块运动没有进入可见高程的主因果链；
- 同类型板块边界被忽略，边界检测还存在硬编码和死路径；
- 海沟、洋中脊、裂谷等配置字段多数未被读取；
- 区域层和细节层幅值相对基础高度过小，量化后接近空操作；
- `Grid` 未使用 world seed，同 seed 不能保证点集复现；
- 地图宽高独立归一化造成 2:1 地图的方向性拉伸；
- `atan2` 直接作为噪声维度会产生径向接缝；
- 海平面、海岸线和后处理之间存在互相冲突的语义；
- 水文原型不能正确保存有向河网，流量类型和填洼算法也不适合完整产品；
- 初始化时同一批点被多次三角剖分；
- 模板显示名与参数匹配字符串不一致，多个模板落到默认参数；
- 当前模板最终坍缩成少量相似宏观布局。

此前 Claude 会话运行过 `cargo test --all-targets --release`，当时结果为 `80 passed / 1 ignored / 0 failed`。这是历史证据，不代表本检查点重新执行了测试。

## 5. 已确认的自然世界路线

推荐的自然生成因果顺序为：

```text
世界法则与天体条件
  → 拓扑与空间尺度
  → 板块与地壳
  → 构造边界事件
  → 高程、海陆与海底
  → 岩性、热点与资源前体
  → 初步气候/降水
  → 水文与侵蚀
  → 最终气候、积雪和冰川
  → 土壤、生态与资源
  → 人口与社会历史
```

关键算法方向：

- 地形采用一次性构造事件场，不做板块时间积分；
- 洋壳年龄可由距活动洋中脊的距离与扩张速度近似；
- 水文使用 `f32` 高程上的 Priority-Flood、排水 DAG 和有向河段；
- 侵蚀使用汇水面积、坡度与岩石硬度，并保存沉积；
- 气候使用低分辨率月度模型，包含纬度、季节气压带、风、水汽平流、地形雨和雨影；
- 水力侵蚀需要降水时，可以使用“初步气候 → 侵蚀 → 最终气候”的双趟流程；
- 自然字段必须带明确单位、有效范围、来源和版本。

## 7. 独立显示模块的已知要求

显示系统必须只消费稳定的世界快照或字段视图，不能调用生成算法，也不能把渲染颜色反写为世界真值。

需要至少支持：

- 连续标量场：高程、温度、降水、魔力密度；
- 分类场：板块、地壳、岩性、生物群落、国家；
- 向量场：板块速度、风、洋流；
- 线与网络：边界段、河流、道路、地脉、传送网络；
- 点与事件：城市、火山、资源点、历史事件；
- 地形成图：分层设色、晕渲、等高线、海岸与水体；
- 调试模式：无效值、字段来源、依赖状态、脏区域和重算范围；
- 时间模式：指定年代快照、变化对比和事件定位。

字段切换、调色板和显示范围应主要通过 GPU 数据与 uniform 完成，不能像当前实现一样每帧在 CPU 重建所有颜色和几何。

显示正确性需要可验证：

- 固定输入的截图基线；
- 字段极值、NaN、缺失值和分类非法值的醒目调试显示；
- CPU 参考采样与 GPU 输出抽查；
- 不同缩放和分辨率下的宏观位置一致性；
- 生成字段与显示图例使用同一单位和范围描述。

## 8. 下一步需要比较的架构方案

恢复讨论后，应先比较至少三种方案，再让用户选择：

1. **固定强类型世界结构**
   - 编译期安全，Rust 使用自然；
   - 增加魔法字段和第三方规则时扩展成本高。

2. **完全动态字段注册表**
   - 规则包和显示模块扩展灵活；
   - 容易失去单位、依赖和类型安全，重演当前字符串字段问题。

3. **强类型核心 + 模式化扩展注册表**
   - 地形、水文、气候、时间和历史等核心契约强类型；
   - 魔法与产品扩展通过带 schema、单位、依赖和版本的字段/事件注册；
   - 普通规则包只能使用公开能力，世界法则包可以显式替换能力；
   - 这是目前最可能的推荐方案，但尚未正式呈现并取得用户批准。

完整系统规模过大，不适合写成一个实施规范。建议先形成一份总体蓝图，再拆成独立规范：

1. 世界要素目录与核心数据契约；
2. 独立显示模块；
3. 自然世界生成；
4. 魔法规则与世界法则；
5. 历史演化与社会系统；
6. 作者工具、持久化与导出。

每个子系统分别经过“设计 → 用户确认 → 实施计划 → 实现”。

## 9. 尚未确认的问题

恢复后首先讨论：

1. **目标时代和历史跨度**：首个内置规则集生成到前工业奇幻、工业时代，还是由规则包定义技术时代？

后续问题按一次一个的方式确认：

- 历史使用固定年代步长、事件驱动，还是二者结合；
- 非人类智慧物种是否是一等公民，以及种族/物种规则的可配置程度；
- 神祇是魔法规则、历史行动者，还是两者兼具；
- 魔法规则包第一阶段只用数据定义，还是立即需要脚本；
- 作者修改历史后采用严格下游重算、分支世界，还是允许锁定矛盾结果；
- 世界快照、编年史和编辑操作的保存与版本迁移边界；
- 首个可验收的“完整纵切”应覆盖哪些自然、魔法和社会要素。
